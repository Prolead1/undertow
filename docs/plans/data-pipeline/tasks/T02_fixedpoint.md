# T02 — Fixed-point & tick math

**Wave 1 · size M · depends on: T00 · blocks: T05, T06, T10, T11**
**Branch:** `feature-data-fixedpoint`

## Why this task exists

Every number the pipeline touches is a fixed-point integer from a Solidity contract: `sqrtPriceX96` in
Q64.96, `feeGrowth*X128` in Q128, ticks on a `1.0001^i` lattice. Roadmap §10.2.4 is explicit that
getting fees *exact* rather than *estimated* is what makes the thesis's on-chain validation real, and
that exactness starts here. If this module is off by one bit, T10's fee numbers are wrong and T13's
reconciliation against real `Collect` events fails with no way to tell whether the bug is here or there.

**This is the module where a `float` is a bug.** `2**128 ≈ 3.4e38`; float64 carries 53 bits of mantissa.
A single `float()` on the path from accumulator to fee amount destroys ~70 bits of precision.

## What to build

Implement `CONTRACTS.md` §3 exactly. Three groups:

### 1. Tick ↔ sqrt price (the hard part)
`tick_to_sqrt_price_x96` and `sqrt_price_x96_to_tick` must be **exact integer reimplementations** of
Uniswap V3's `TickMath.getSqrtRatioAtTick` / `getTickAtSqrtRatio` — the magic-constant binary
decomposition (`0xfffcb933bd6fad37aa2d162d1a594001`, …) and the bit-length + log2 approximation
respectively. Port them faithfully; do not substitute `int(1.0001 ** (tick/2) * 2**96)`, which drifts by
several units at large |tick| and will not round-trip.

Semantics: `getTickAtSqrtRatio` has **floor** semantics — it returns the greatest tick whose
`getSqrtRatioAtTick` is `<= ` the input. `PLAN.md` §7 pins this: the roadmap's `tick =
round(log(price)/log(1.0001))` is a pedagogical simplification; the protocol floors.

### 2. Price conversions (`Decimal`, never `float`)

**Read `CONTRACTS.md` §3.0 in full before writing this function.** It pins the orientation, gives the
formula, and gives a worked numeric check. Summary:

```
price_token1_in_token0 = 10**(dec1 - dec0) * 2**192 / sqrt_price_x96**2
```

returning the price of **token1 denominated in token0, in human units** — for the pinned pools, **USDC
per WETH**, the familiar "ETH price in dollars", ~2000–4000 across the window.

Note this is the **reciprocal** of the naive `(sqrt_price_x96 / 2**96)**2 * 10**(dec0 - dec1)`, which
returns WETH per USDC (~3.3e-4). Both are valid arithmetic; only one is the convention, and picking the
wrong one silently inverts every impermanent-loss number in the thesis. §3.0 has the worked check
(`sqrt_price_x96 = 1446501726624926496477173928747177` ⇒ `3000.000…`) — transcribe it as a test.

Consequence to internalize and assert: because the raw tick price `1.0001**tick` is
raw-token1-per-raw-token0, the human price is **decreasing** in tick for these pools, and the pool's tick
is **positive** (~+190k to +210k). §3.0 has a five-row tick↔price anchor table; use it.

Compute with exact integer numerator/denominator into a `Decimal`; guard `sqrt_price_x96 == 0`.

Use `decimal.Decimal` with a locally-set context precision (≥60 digits), restored on exit — do not
mutate global decimal context.

### 3. Wrapping arithmetic + liquidity math
- `wrapping_sub_256` / `wrapping_add_256` — mod `2**256`. Required because Uniswap computes fee-growth
  deltas in `unchecked` blocks and the accumulators genuinely wrap. T10 depends on this.
- `q128_to_decimal` — exact `Decimal` division by `2**128`.
- `get_amount0_delta` / `get_amount1_delta` / `liquidity_for_amounts` / `amounts_for_liquidity` — ports
  of `SqrtPriceMath` / `LiquidityAmounts`, integer, with the protocol's floor/ceil rounding direction
  (`round_up` argument). These are what T13 uses to separate principal from fees in a `Burn`+`Collect`
  pair and what T11 uses to value a position.
- `align_tick_down` / `align_tick_up` — **must be correct for negative ticks**. Python's floor division
  already floors toward −∞, which is what the protocol wants for `tickLower`; C-style truncation is
  wrong. Test with `tick = -61, spacing = 60 → -120`.

## The fixture you must create

`tests/data/fixtures/tickmath_vectors.json`: a list of `{"tick": int, "sqrt_price_x96": "decimal
string"}` pairs covering `MIN_TICK`, `MIN_TICK+1`, `-887000`, `-100000`, `-60`, `-1`, `0`, `1`, `60`,
`100000`, `196256` (the §3.0 $3000 anchor for the pinned pool), `887000`, `MAX_TICK`, plus a few arbitrary
mid-range ticks.

**A fixture generated by the code it tests proves nothing** — the reviewer is instructed to look for
exactly that. So anchor it independently. In descending order of preference:

1. Transcribe from Uniswap **v3-core**'s `test/TickMath.spec.ts` / its snapshot files, which contain
   published tick→sqrtRatio pairs. Cite file and line in the fixture header.
2. Failing that, the four values pinned in `CONTRACTS.md` §3.0 (the $3000 anchor) and the well-known
   boundary constants `MIN_SQRT_RATIO` (the sqrt ratio at `MIN_TICK`, a 10-digit integer) and
   `MAX_SQRT_RATIO = 1461446703485210103287273052203988822378723970342`, which appear verbatim in
   `TickMath.sol` — these three alone pin both ends and the middle of the curve.
3. Cross-check a handful with an independent high-precision computation:
   `int(Decimal("1.0001")**(Decimal(tick)/2) * 2**96)` at 60-digit precision agrees with the Solidity
   port to within a unit or two for mid-range ticks. Agreement to ±2 is a meaningful check that your
   magic constants were transcribed correctly; it is **not** a substitute for exact vectors at the
   boundaries, where the approximation drifts.

**State in your PR which route you used for which vectors.**

## Tests you must write

1. Round-trip `sqrt_price_x96_to_tick(tick_to_sqrt_price_x96(t)) == t` for every fixture tick.
2. `tick_to_sqrt_price_x96` equals the fixture value **exactly** (integer equality) for every vector.
3. Monotonicity: `tick_to_sqrt_price_x96` strictly increasing across a sweep of ticks.
4. Floor semantics: for `t` in the sweep, `sqrt_price_x96_to_tick(tick_to_sqrt_price_x96(t) + 1) == t`
   and `sqrt_price_x96_to_tick(tick_to_sqrt_price_x96(t) - 1) == t - 1`.
5. Out-of-domain: `tick_to_sqrt_price_x96(MAX_TICK + 1)` raises; ditto below `MIN_TICK`.
6. Price orientation, three assertions: (a) `sqrt_price_x96_to_price(1446501726624926496477173928747177,
   6, 18)` == 3000 to 20 significant digits (§3.0's worked check); (b) `tick_to_price` reproduces
   §3.0's five-row anchor table to within a basis point; (c) `tick_to_price` is **decreasing** in tick
   for `(dec0, dec1) = (6, 18)` — the direction that surprises everyone once.
6b. `price_to_sqrt_price_x96` round-trips with `sqrt_price_x96_to_price` to within 1 unit, and
   `sqrt_price_x96_to_price(0, ...)` raises.
7. `wrapping_sub_256(0, 1) == 2**256 - 1`; `wrapping_add_256(2**256 - 1, 1) == 0`.
8. Negative-tick grid alignment: `align_tick_down(-61, 60) == -120`, `align_tick_up(-61, 60) == -60`,
   and both are idempotent on already-aligned ticks.
9. `amounts_for_liquidity` / `liquidity_for_amounts` round-trip within the protocol's 1-wei rounding
   tolerance, tested for price **below**, **inside**, and **above** the range (three different
   branches — all three must be covered).
10. **No-float guard:** an `ast` walk over `fixedpoint.py` asserting the module contains no `float(`
    call and no float literal in a return expression. Blunt, but it is the invariant that matters and it
    keeps working after you leave.
